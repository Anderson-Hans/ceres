# ADR-03. Временные метки, PIT-срез, диагностики и воздержание

**Статус:** Proposed
**Версия:** 1.1 (2026-09-27)
**История:** 1.0 — первичная версия (commit 9d4ebc2). 1.1 — уточнено, что маркер базиса при отсутствии входов даёт NOT_EVALUATED (ADR-04 v1.1); без изменений по существу.
**Затрагивает:** §4, §5.1, §5.2, §6.4, §7.2 спецификации v0.2
**Тип:** [ADR]

## Контекст

- §5.1: `Observer.fetch(as_of: date)`, но запись §4 имеет `as_of` —
  timestamp (`2026-06-15T20:00:00Z`). WASDE выходит в середине торговой
  сессии, Crop Progress — после закрытия: дата без времени не позволяет
  корректно отсечь публикации внутри дня.
- §4: правило воздержания ссылается на «порог режима» ширины интервала
  и «порог» `prior_shift`, не определяя ни формулу `prior_shift`, ни пороги.
- §7.2: `r_hat < 1.01` задан; минимум `n_eff` не задан.
- §4 JSON требует `n_eff`, `r_hat`, но для B0/B1 MCMC нет.

## Решение (предлагаемое)

### 1. Время

- Все внутренние срезы — timezone-aware UTC `datetime`. Naive-datetime
  в коде PIT-слоя — ошибка (тест).
- Интерфейс §5.1 адаптируется: `fetch(as_of: datetime) -> list[Evidence]`,
  где `as_of` — tz-aware UTC. Прежняя сигнатура с `date` не
  поддерживается (передача `date` — `TypeError`). Поля `Evidence` §5.1
  сохраняются без изменений; дополнительное provenance — в связанной
  таблице (ADR-08).
- **Ежедневный срез `as_of_t`** = 18:00 America/Chicago торговой даты `t`,
  переведённое в UTC (с учётом перехода на летнее время). Обоснование:
  после публикации дневного settlement зерновых CBOT и до открытия
  вечерней сессии следующей торговой даты (время открытия — подлежит
  проверке по расписанию CME для каждой исторической эпохи; если в
  какую-то эпоху settlement публиковался позже 18:00 CT, срез этой эпохи
  сдвигается, изменение фиксируется в ADR до данных).
- Факт виден в срезе, если `vintage_time <= as_of` (включительно).
  Порядок: фильтр по `vintage_time` → последняя допустимая ревизия
  логического факта → признаки.
- `vintage_time` = официальное время публикации (дата и время из
  календаря источника, в UTC). Если известна только дата публикации —
  консервативно `23:59:59` местного времени источника этой даты (то есть
  факт становится доступен в срезе следующей торговой даты). Если
  неизвестна и дата — факт исключается из честной исторической проверки
  и помечается `vintage_confidence = unknown`.
- `retrieved_at` не используется как `vintage_time`.

### 2. `prior_shift`

`prior_shift(t) = | p_up(model) − p_up(B0) |`, шкала — вероятностные
пункты `[0, 1]`. Априор — основной B0 (ADR-01), единый для всех моделей,
поэтому величина сравнима между B1, B2, B3.

Порог — не число, а зарегистрированное правило:
`prior_shift(t) < z · sd_post(p_up(model))` → ABSTAIN
(`abstain_reason = "PRIOR_SHIFT_BELOW_THRESHOLD"`), где `sd_post` —
апостериорное стандартное отклонение `P(R>0)` (для B1 — из Beta-апостериора
с учётом формулы `p_up` ADR-01; для B2+ — по MCMC-выборке),
`z = 1.645` (односторонние 95%). Смысл: сдвиг от климатологии
неотличим от неопределённости собственной оценки. Для B0 публикация
невозможна по определению (B0 — baseline).

### 3. Ширина 90% интервала

`width90(t) = q0.95 − q0.05` предиктивного распределения `R(t,H)`.
Порог: `width90(t) > width90_B0(t)` → ABSTAIN
(`"INTERVAL_TOO_WIDE"`) — модель не острее климатологии той же сезонной
позиции. «Режим» до B4: `{normal, zw_post_2022}`; для ZW публикация
SIGNAL в v1 не допускается вовсе (ADR-05, роль стресс-теста), поэтому
отдельный порог режима до B4 не требуется. B4 вводит режим-зависимые
пороги своим ADR.

### 4. MCMC-диагностики (B2+)

- Проверяемые параметры: все параметры верхнего уровня иерархии
  (гиперсредние, гиперсигмы), параметры наблюдения (масштаб, степени
  свободы при их наличии), полужизнь дисконтирования, а также
  предиктивные `p_up` и квантили на каждом прогнозном дне.
- `r_hat` (rank-normalized split R-hat) `< 1.01` — из v0.2.
- **Предложение исполнителя, не требование v0.2:** bulk-ESS и tail-ESS
  `≥ 400` для каждого проверяемого параметра (4 цепи; ориентир из
  литературы по rank-normalized R-hat/ESS). Число divergent transitions
  после warmup — `0`; иначе публикация блокируется.
- Провал любой проверки → ABSTAIN `"MCMC_DIAGNOSTICS_FAILED"`,
  распределение сохраняется как исследовательский результат с причиной.

### 5. Поля `n_eff`, `r_hat` для не-MCMC моделей

Схема записи версии `1.0.0` расширяет §4 полем `posterior.inference`:
`"closed_form" | "empirical" | "nuts"`. Для `closed_form`/`empirical`:
`n_eff = null`, `r_hat = null`. Фиктивные `r_hat = 1`, `n_eff = число
строк` запрещены. Для `nuts` — минимальное значение по проверяемым
параметрам.

### 6. Обязательные источники и свежесть

| Фаза / модель | Обязательные источники |
|---|---|
| Фаза 1: B0 | цены (settlement контракта) |
| Фаза 1: B1 | цены + WASDE (признак ADR-09) |
| Фаза 2: B2 | как B1 + источники признаков, зарегистрированных для B2 |
| Фаза 3 | + принятые наблюдатели (по результатам абляций) |

Свежесть: месячное значение актуально до следующего **планового**
релиза + grace 2 рабочих дня. Статусы: `not_yet_due` (норма),
`delayed` (плановая дата прошла, grace не истёк — значение ещё
допустимо, маркер), `missing` (grace истёк — ABSTAIN
`"REQUIRED_SOURCE_MISSING"`), `invalid` (парсер/валидация отвергли —
ABSTAIN `"REQUIRED_SOURCE_INVALID"`), `cancelled` (релиз официально
отменён, например из-за приостановки работы правительства — после grace
ABSTAIN). Для replay статус вычисляется по историческому календарю и
историческим фактам публикации, а не по сегодняшней доступности сервиса.

### 7. Допуски калибровки/coverage (фаза 2, гейт п. 2)

Предложение:
- coverage 90%-интервала на полной OOS-выборке: точечная оценка в
  `[0.85, 0.95]` **и** блочный 95% ДИ содержит `0.90`;
- калибровка `p_up`: логистическая рекалибровка `logit(o) ~ a + b·logit(p)`
  на OOS; блочные 95% ДИ содержат `a = 0` и `b = 1`; reliability diagram
  (10 бинов) публикуется всегда.

### 8. ABSTAIN без валидного posterior

Если распределение не вычислено (нет данных, пустой класс, провал
вывода), запись содержит `decision = "ABSTAIN"`, `abstain_reason`,
`posterior = null`. Никаких `p_up = 0.5`, нулевых квантилей или
`severity = "none"` для невычисленного. Все причины сохраняются в
`abstain_reasons: [...]` (расширение схемы 1.0.0); `abstain_reason` —
первая по фиксированному приоритету:
`PIT_VIOLATION > UNSUPPORTED_CONTRACT_OR_HORIZON > MODEL_NOT_ACCEPTED >
REQUIRED_SOURCE_MISSING > REQUIRED_SOURCE_INVALID > PRICE_MISSING >
MCMC_DIAGNOSTICS_FAILED > POSTERIOR_INVALID > B1_EMPTY_CLASS >
MARKET_ANOMALY_HIGH > REGIME_BREAK_HIGH > MARKER_NOT_EVALUATED >
INSTRUMENT_ROLE_STRESS_TEST > INTERVAL_TOO_WIDE > PRIOR_SHIFT_BELOW_THRESHOLD`.

Маркер со статусом `NOT_EVALUATED` отличается от `severity = "none"`;
если маркер обязателен для фазы, `NOT_EVALUATED` → ABSTAIN.

## Последствия

- Изменение схемы записи версионируется (JSON Schema в `schemas/`,
  появится в фазе 0).
- Пороги не подбираются по OOS: они являются функциями training-оценок
  и собственной неопределённости модели.
- Ожидаемая доля ABSTAIN 60–85% (§4) — диагностика, не цель настройки.
